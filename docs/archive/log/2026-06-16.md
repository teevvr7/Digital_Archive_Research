## What was built (Milestone E)

### Core extraction module — `backend/app/modules/idp/extraction.py`
Full VLM structured-extraction pipeline wired into the IDP worker:

- **Text mode** (digital PDFs with text layer): extracted text chunked by token budget → per-chunk VLM calls → merged result. Free path — no image rendering, no GPU image overhead.
- **Vision mode** (scans / images, no text layer): page images rasterized @ 120 DPI, resized to 512 px, batched across VLM calls → merged result.
- **Chunk/merge** (`_merge_extractions`): `line_items` concatenate across chunks; scalars take first non-empty; total/amount keys take last non-empty (grand total lives on the final page).
- **Tolerant parse** (`_tolerant_parse`): strips ` ```json ` fences → balanced-brace extraction → truncation repair → retry. Saves outputs cut off by the 256-token cap.
- Config-driven budgeting: `VLM_MAX_MODEL_LEN`, `VLM_MAX_OUTPUT_TOKENS`, `VLM_MAX_CHUNK_CALLS` in `.env`.

## Bug fixed: only 4 line items from 70-item invoice

### Symptom
`big-invoice.pdf` (Oriental Merchant Pty Ltd, 4 pages, ~70 SKUs, 10,788 chars) returned only 4–5 line items in the Extracted Data UI tab.

### Root cause
Single-phase VLM call: the 256-token output budget was shared between header fields (vendor, invoice number, totals, buyer, etc.) and line items. The model filled the header first, then only had room for a handful of items. It also chose "representative" items rather than exhaustive listing.

### Fix: two-phase extraction (`_extract_two_phase`)

**Phase 1 — header only** (first text chunk, `_HEADER_PROMPT`):
- Extracts: `vendor`, `invoice_number`, `invoice_date`, `total_amount`, `currency`, `buyer`, `buyer_address`, `vendor_address`, `gst`, `grand_total`, `terms_conditions`
- Explicitly told: "do NOT include line_items"
- Full 256-token budget → clean header with no SKU clutter

**Phase 2 — line items only** (all chunks, `_LINE_ITEMS_PROMPT`):
- Extracts: `line_items[{code, description, qty, unit_price, amount}]`
- Told: "Include EVERY product/service row visible — do not skip any"
- 6–9 separate chunk calls, each with 256 tokens for items only → ~12 items/call

**Config change**: `VLM_MAX_CHUNK_CALLS=6 → 10` (1 header call + up to 9 item-chunk calls).

### Secondary fix: `_repair_truncated_json` dangling key bug
When the VLM output was truncated mid-key-name (e.g., `"descriptio`), the repair function appended a closing `"` → produced a dangling closed string (`,"descriptio"`) that existing regexes didn't remove, causing the chunk to be unparseable.

**Fix**: added a third cleanup pass:
```python
# Drop a dangling key string (closed but no colon+value follows)
res = re.sub(r'[,{[]\s*"[^"]*"\s*$', lambda m: m.group(0)[0], res)
res = re.sub(r",\s*$", "", res)  # second trailing-comma pass
```
