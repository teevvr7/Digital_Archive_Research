# Milestone C — IDP Text-Extraction Pipeline

## Context

Milestones A (login → bootstrap → dashboard) and B (upload → store → list → download, 9/9 isolation tests green) are complete. Uploaded documents currently sit at status `queued` forever — the worker loop was intentionally deferred to Milestone C.

This milestone makes the **async extraction loop real and testable end-to-end** without any GPU cost: upload → enqueue → worker downloads the file → extracts text (free text-layer path for digital PDFs, OCR fallback for scanned docs/images) → stores `extracted_text`, populates the `search_tsv` index, and drives the document through its status states to `completed`. This unblocks search (Milestone D) and provides clean, raw text for the VLM structured-JSON step (the milestone after this one).

**Decisions confirmed with user:**
- **Scope:** text extraction only now. VLM structured-JSON deferred to next milestone (build a clean seam, don't build VLM).
- **OCR engine:** RapidOCR (`rapidocr-onnxruntime`) — pip-only, no system binaries, Windows-friendly, free, CPU-only. We will measure its performance on a sample scanned doc.
- **VLM endpoint:** not set up; not needed this milestone.

**Cost-first design (priority #1):** PyMuPDF reads the embedded text layer for free on the ~85% of docs that are digital PDFs. OCR (the expensive path) runs **only** when there is no usable text layer. This is the single biggest cost lever.

## How It Works — Storage, Text Extraction, and the IDP Vision

### Where documents are stored (and what lives where)
Two stores, strict separation — **file bytes never touch the database**:

- **Object storage (Supabase Storage, private `documents` bucket)** holds the raw file bytes only, at key `{tenant_id}/docs/{doc_id}.{ext}` (e.g. `…/docs/ab12….pdf`). The `tenant_id` prefix keeps each tenant's files in their own path. Files are written once on upload (`storage.upload_file`) and read back by the worker (`storage.download_file`); users download via short-lived signed URLs (`create_signed_url`, 5-min expiry) — the bucket is never public.
- **Postgres (Supabase DB)** holds only *metadata and derived data*: the `documents` row (filename, mime, size, `storage_key` pointer, status, page count, flags) and — after this milestone — the **`extracted_text`** and the **`search_tsv`** index. Every row carries `tenant_id` and is fenced by Row-Level Security.

Why split this way (cost is priority #1): object storage is far cheaper per GB than a database, and keeping bytes out of Postgres keeps the DB small, fast, and cheap to back up. The DB stores only what we need to *search and reason over*.

### What the extracted text is for
The worker turns each file into plain text. Two text paths, chosen per-document to minimise cost:
- **Text-layer path (free, ~85% of docs):** digital PDFs already contain an embedded text layer — PyMuPDF reads it directly, no AI, no OCR, near-instant.
- **OCR path (only when needed):** scanned PDFs and images have no text layer, so we rasterise each page to an image and run RapidOCR on it. This is the expensive path, so it runs *only* when the text layer is missing.

That extracted text immediately powers two things:
1. **Search (next milestone, D):** `search_tsv` is a Postgres full-text index built from the text — it makes "find every document mentioning X" fast (<2s target) with no external search cluster.
2. **Structured extraction input (IDP, the milestone after):** clean raw text + page images are exactly what the VLM step consumes to produce structured JSON.

### The bigger IDP picture (where this fits)
The full **Intelligent Document Processing** vision is a cost cascade — cheap stages first, the GPU only on novelty:

```
upload → [THIS MILESTONE: text extraction] → classify/fingerprint → cheap deterministic
         text-layer or OCR → raw text          (future)             extract OR VLM→JSON
                                                                     (future, GPU only on
                                                                      novel/low-confidence)
                                                          → confidence gate → store + index
```

This milestone builds the **foundation layer** — getting reliable text out of every document. Future steps (separate milestones) layer intelligence on top of that text:
- **VLM → structured JSON:** send page image + text to the Lightning AI vLLM (Qwen2.5-VL) to extract typed fields (invoice number, total, dates…) into `extracted_data`, with a confidence gate.
- **Self-learning loop:** record every attempt in `extractions`; once a layout is confirmed N times, "promote" it to a deterministic template (`document_templates`) so future identical docs skip the GPU entirely — driving cost down over time.

The DB schema (`extractions`, `document_templates`, `document_types`, plus `extracted_data`/`confidence`/`ai_extraction` status) is **already built for all of this** — this milestone just fills the first stage and leaves clean seams for the rest.

## Implementation

### 1. Dependencies — `backend/pyproject.toml`
In the `[worker]` optional extra, replace the unused `liteparse>=2.0.0b2` (Rust beta, unverified Windows install) with `rapidocr-onnxruntime>=1.3`. Keep `pymupdf>=1.24` and `pillow>=10.3`. Leave `openai`/`jsonschema` for the VLM milestone (lightweight, pure-pip).
> Rationale: user chose RapidOCR; LiteParse is unused in this scope and a Windows install risk. Noted as a deliberate deviation from CLAUDE.md §2.

### 2. New module `backend/app/modules/idp/`
- **`ocr.py`** — RapidOCR wrapper. Lazy module-level singleton (model init is heavy — load once per worker process). `ocr_image(png_bytes) -> tuple[str, float]` returning text + mean confidence.
- **`parsing.py`** — PyMuPDF helpers: `open_pdf(bytes)`, `page_count`, `extract_text_layer(doc) -> str`, `has_usable_text_layer(text)` (threshold on non-whitespace chars/page), `rasterize_page(page) -> png_bytes` (for OCR input and reused later by VLM).
- **`pipeline.py`** — orchestrator `run_extraction(file_bytes, mime_type) -> ExtractionResult` (dataclass: `text`, `page_count`, `has_text_layer`, `ocr_used`, `ocr_confidence`). Logic:
  1. PDF → open with PyMuPDF, get `page_count`, try text layer. If usable → use it, `ocr_used=False`.
  2. PDF with no usable text layer → rasterize each page → RapidOCR → concatenate text, average confidence, `ocr_used=True`.
  3. Image mime → RapidOCR directly, `page_count=1`, `ocr_used=True`.
  Emit per-stage timing to logs (so user can evaluate RapidOCR performance).
- **`jobs.py`** — `process_document(doc_id: str, tenant_id: str)` — the enqueued RQ entrypoint. Opens `tenant_session(tenant_id)`; loads `Document` + its `ProcessingJob`; on missing row raises (RQ retry handles upload→commit race). Drives:
  - `ProcessingJob` → running, `started_at=now`, stage transitions; `Document.status` → `extracting_text` then `ocr_processing` if OCR used.
  - `download_file(storage_key)` → `run_extraction(...)`.
  - Persist `extracted_text`, `page_count`, `has_text_layer`, `ocr_used`, `ocr_confidence`; set `Document.status=completed`, `processed_at=now`.
  - Populate `search_tsv` via Postgres: `update(Document).values(search_tsv=func.to_tsvector('english', combined_text))` over filename + extracted_text (no DB trigger/migration needed — keeps scope minimal).
  - `ProcessingJob` → completed, `finished_at`, `duration_ms`; write `processing_complete` ActivityEvent.
  - **On any exception:** rollback, set `Document.status=failed` + `error_message`, `ProcessingJob` failed + `error`, increment `attempts`, write `processing_failed` ActivityEvent.
- **`queue.py`** — `enqueue_document(doc_id, tenant_id)` wrapping `Queue(settings.idp_queue_name, ...).enqueue("app.modules.idp.jobs.process_document", ..., retry=Retry(max=3, interval=[10,30,60]))`. Single public seam the files module imports — keeps RQ out of `files/`.

### 3. Wire enqueue — `backend/app/modules/files/service.py`
In `create_documents` and `retry_document`, enqueue **after commit** to avoid the worker racing an uncommitted row. Use a SQLAlchemy `event.listen(db, "after_commit", ...)` hook capturing the created `(doc_id, tenant_id)` pairs and calling `enqueue_document`. RQ `Retry` is defense-in-depth. Remove the "deferred to Milestone C" comment.
> Cross-module call goes through `idp.queue.enqueue_document` (service-layer boundary), per CLAUDE.md module rules.

### 4. Frontend — minimal visibility for validation
- Add `extracted_text` → `extractedText` to `DocumentOut` (`backend/app/modules/files/schemas.py` + `_doc_to_out` in `service.py`). camelCase contract test auto-covers it.
- `frontend/app/(app)/documents/[id]/page.tsx`: in the "Extracted Data" tab, when there is no structured `extractedData` yet but `extractedText` exists, render a read-only **Extracted Text** panel. Lets the user see extraction working before VLM exists. Status badges already cover the new states — no badge changes needed.
