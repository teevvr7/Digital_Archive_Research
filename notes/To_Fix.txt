DATAWIZ IDP ARCHITECTURAL ISSUES & PROPOSED IMPROVEMENTS

This document outlines structural flaws, limitations, and recommendations for the IDP system to ensure that custom configurations (instructions, rules, schemas) are correctly processed and structured without interfering with teammate workflows.

================================================================================
1. ISSUE: TENANT-WIDE CUSTOMIZATION BYPASS (BUG)
================================================================================
* Description:
  Custom instructions, rules, and JSON schemas saved in the IDP Control Center
  are completely ignored during extraction for new uploads. The background
  worker falls back to the static, global system-default DocumentType schema.
* Root Cause:
  The background worker (jobs.py) and pipeline orchestrator (pipeline.py) only
  look up customized templates if `doc.template_id` is explicitly set. Since new
  document uploads have no layout fingerprint or template resolved yet,
  `doc.template_id` is None, causing the system to bypass the tenant's promoted
  template containing the custom settings.
* Immediate Patch:
  Modify strategy and schema resolution to search for a tenant's promoted
  DocumentTemplate matching the document's type if `doc.template_id` is None:
  `template = db.query(DocumentTemplate).filter(DocumentTemplate.document_type_id == doc.document_type_id, DocumentTemplate.tenant_id == doc.tenant_id, DocumentTemplate.status == "promoted").first()`
* Long-Term Fix:
  Decouple tenant settings from visual layouts (see Section 4).

================================================================================
2. LIMITATION: POSTGRESQL JSONB KEY REORDERING (LLM PROMPT DEGRADATION)
================================================================================
* Description:
  PostgreSQL stores dynamic schemas inside `JSONB` columns. Since JSONB normalizes
  and alphabetically reorders keys on write, the original layout order designed
  by the admin in the UI is lost. This disrupts Qwen-VL's linear extraction flow,
  leading to degraded performance and accuracy.
* Immediate Patch (Metadata String Serialization):
  Save the raw, ordered schema string inside the JSONB payload under a metadata
  key `_original_schema_str` during config updates. Parse this string using
  `json.loads()` on load to reconstruct the dictionary in the exact user-defined
  order before compiling the system prompt for Qwen.
* Long-Term Fix (Structured JSON Arrays):
  Change the schema design to represent the target structure as a JSON array of
  field definition objects rather than a JSON object:
  `[{"key": "document_details", "type": "object", "fields": [...]}, ...]`
  PostgreSQL JSONB arrays never reorder elements, naturally preserving the sequence
  without duplicate storage or string parsing workarounds.

================================================================================
3. ISSUE: SILENT MOCK FALLBACKS IN PRODUCTION
================================================================================
* Description:
  When the remote GPU server is offline or fails, the extraction pipeline falls
  back to generating mock data in development mode. While convenient for offline
  local testing, this behavior is dangerous in staging or production because it
  hides configuration and network failures.
* Resolution:
  Introduce an explicit `allow_mock_fallback` boolean configuration parameter
  (defaulting to False). If False, connection and model execution errors must
  propagate immediately, causing the worker job to fail visibly and mark the
  document status as FAILED.

================================================================================
4. ARCHITECTURAL IMPROVEMENT: DECOUPLING SETTINGS FROM VISUAL LAYOUTS
================================================================================
* Current Design:
  The system uses the `DocumentTemplate` model to store both:
  1. Tenant-wide general IDP configuration (System Instructions, Rules, Schema).
  2. Visual coordinates and deterministic CPU mappings (Phase 2 Layouts).
  This conflation will cause conflicts once visual layout matching is enabled,
  as general tenant configurations will be overwritten by layout-specific matching.
* Recommended Structure:
  1. Create a dedicated `idp_settings` table for tenant-global configs:
     - `tenant_id` (UUID)
     - `document_type_id` (UUID)
     - `extraction_method` (String)
     - `instruction` (Text)
     - `rules` (Text)
     - `json_schema` (JSONB)
  2. Keep `document_templates` restricted purely to layout-specific visual mappings.
  3. Update the pipeline configuration loader to follow a strict hierarchy:
     `Document -> Match Visual Layout -> If Yes, use Layout Template -> Else, use Tenant IDP Settings -> Else, use Global Document Type Defaults`
